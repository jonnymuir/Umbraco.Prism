# Skill: Walkthroughs Are Executable Specs

**Audience:** Anyone authoring or modifying a walkthrough under `docs/walkthroughs/`.
**Status:** Mandatory.

## Principle

Behaviours of PRISM are captured as **tests**. Walkthroughs describe **how to
configure** the system and **show those tested behaviours working**. There is
exactly one source of truth per behaviour: the test. The walkthrough narrates
around it and embeds the screenshots the test produces.

Three artefacts must stay in lockstep for every walkthrough:

1. `docs/walkthroughs/{key}.md` — the human narrative (configuration, outcome,
   embedded screenshots).
2. `src/UmbracoPrism.Client/tests/walkthroughs/{key}.walkthrough.spec.ts` — the
   executable counterpart that asserts the behaviour and (when
   `CAPTURE_SCREENSHOTS=1`) writes screenshots into
   `docs/images/walkthroughs/{key}/`.
3. `docs/images/walkthroughs/{key}/*.png` — generated by (2), embedded by (1).

If any of these three drifts from the others, the walkthrough is broken.

## Rules

### R1 — Every walkthrough has an executable spec

Either a Playwright spec file under `tests/walkthroughs/`, or — for scenarios
that genuinely cannot be automated end-to-end (e.g. iOS device biometrics) —
a partial spec covering everything that *can* be automated, plus a clearly
marked manual capture procedure in the markdown. **Pure-prose walkthroughs are
not allowed.**

### R2 — The spec gates PR CI

The spec runs on every PR via the standard `localhost-auth-playwright` lane.
A flow regression breaks the PR. Screenshot writing is gated by
`CAPTURE_SCREENSHOTS=1` (set only by `.github/workflows/capture-screenshots.yml`,
manual `workflow_dispatch`); behaviour assertions run unconditionally.

### R3 — Assert before you shoot

Every screenshot is preceded by an `assertHealthyPage(page, { url, heading })`
call (or the equivalent `step()` helper) that verifies:

- URL matches the expected pattern.
- Expected heading is visible.
- Body contains no error markers (`/404|Not Found|Page not found|An error
  occurred|Server Error/i`).
- No `.govuk-error-summary` is present on a happy-path step.

Past incident: a walkthrough screenshot silently captured a 404 page because
the spec navigated to a stale URL and only checked that *something* loaded.
This rule prevents that class of failure.

### R4 — Screenshot filenames are deterministic and ordered

Use `NN-slug.png` (e.g. `01-initial.png`, `02-form-filled.png`). The markdown
embeds them in NN order. Renaming a screenshot is a breaking change to the
walkthrough and must be done in the same commit as the spec change.

### R5 — Spec ↔ markdown back-reference

Every walkthrough markdown ends with:

```markdown
---
**Executable spec:** This walkthrough is executed on every PR by
[`{key}.walkthrough.spec.ts`](../../src/UmbracoPrism.Client/tests/walkthroughs/{key}.walkthrough.spec.ts).
Screenshots above regenerate via the [`Capture Walkthrough Screenshots`](../../.github/workflows/capture-screenshots.yml)
workflow (manual dispatch).
```

Every spec file starts with a block comment linking back to the markdown.

### R6 — Negative paths live with the walkthrough

If a workflow has documented validation rules, conditional reveals, or
edge cases, those scenarios live as additional `test(...)` blocks in the
**same** spec file as the happy path, not in a separate "all-demos" file.
One spec = one walkthrough = one source of truth.

## Helper API

`tests/walkthroughs/support/walkthrough.ts` exports:

```ts
export interface PageHealthCheck {
  url: RegExp;
  heading: string | RegExp;
  /** Override default error-marker regex. */
  bodyMustNotContain?: RegExp;
  /** Skip the heading check (e.g. confirmation panels). */
  skipHeading?: boolean;
}

export async function assertHealthyPage(page: Page, expected: PageHealthCheck): Promise<void>;

export async function step(
  page: Page,
  filename: string,           // "01-initial.png"
  expected: PageHealthCheck,
  walkthroughKey: string      // "community-enquiry"
): Promise<void>;             // asserts + (if CAPTURE=1) screenshots
```

Specs use `step()`, never `page.screenshot()` directly.

## Adding a new walkthrough — checklist

- [ ] Create `tests/walkthroughs/{key}.walkthrough.spec.ts` with a top-level
      describe block named after the walkthrough.
- [ ] Add the spec file to `playwright.localhost-auth.config.ts` testMatch.
- [ ] Use `step()` for every captured moment — never bare screenshots.
- [ ] Add `tests/walkthroughs/{key}.walkthrough.spec.ts` happy-path test.
- [ ] Migrate or add edge-case tests in the same spec.
- [ ] Create `docs/walkthroughs/{key}.md` with the embedded screenshots and
      the R5 footer.
- [ ] Run capture workflow once (`workflow_dispatch`) to populate
      `docs/images/walkthroughs/{key}/`.
- [ ] Verify the markdown renders correctly with all images present.

## When automation isn't possible

Some walkthroughs (e.g. mobile biometric prompts, some Umbraco backoffice
flows requiring real OAuth) cannot be fully automated. In that case:

- The spec covers everything *up to* the manual step (e.g. logging in to the
  backoffice, navigating to the tenant page).
- The markdown clearly marks `<!-- manual capture: {reason} -->` next to each
  manually-captured screenshot.
- The reviewer must compare manually-captured screenshots against the running
  app on every relevant PR. (We accept this as a smaller blast radius than
  unbounded prose.)
