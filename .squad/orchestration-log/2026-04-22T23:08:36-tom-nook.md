**Outcome:** Recommendation to remove authored stepType; derive runtime shell from component tree.

## Summary

Tom Nook reviewed the architectural implications of stepType in a component-based workflow system. Core finding: **stepType is an authoring burden and engine derivation is safer than author specification**.

## Decision

Remove `stepType` from authored workflow JSON (`StepDefinition`). Engine infers a **derived `shell`** property on responses (`StepContent`) based on component tree structure.

### Inference Rules

| Condition | Derived shell |
|---|---|
| Any component of type `waiting` present | `"waiting"` |
| All data-carrying components are `summary-list` | `"check-answers"` |
| Has `panel` component, no fieldset/input components | `"confirmation"` |
| Has `task-list` component | `"task-list"` |
| Otherwise (has `fieldset` components with input fields) | `"question"` |

### What Changes

- `StepDefinition.StepType` removed (breaking change; seed migration required).
- `StepContent.StepType` renamed to `StepContent.Shell`.
- `WaitingConfig` promoted from sidecar to first-class component type.
- Existing seed files (payment-demo-v1.json, planning-notification-v1.json) converted: remove `"stepType"`, convert `"waitingConfig"` sidecar to `"waiting"` component.

### What Stays Stable

- `fieldKey` remains on `FieldFile` inside container components (fieldset, summary-list, accordion).
- Validation, error messages, GDS classes: unchanged. Bound to `fieldKey` via `WorkflowProblem`.
- Conditional visibility: unchanged.
- Polling mechanism: unchanged (same JS, same endpoint) — only data source moves from sidecar to `waiting` component.

## Trade-offs

| Pro | Con |
|---|---|
| Authors never declare stepType redundantly | Engine inference rules are new logic (small but testable) |
| Component tree is fully self-describing | Silent contradiction becomes runtime inference, not parse error |
| `waiting` as a component makes it composable | Seed migration required |
| Removes class of authoring errors | |
