## Summary

Blathers verified technical feasibility for unifying fields and components by removing the field/component distinction and deleting stepType. Conclusion: **architecture is already component-agnostic at validation and rendering layers**.

## Risk Assessment

### ✅ LOW RISK (Already Safe)

**Validation & Error Rendering**
- `WorkflowFieldValidator` operates on `IReadOnlyList<FieldRenderPayload>` with **zero component awareness**.
- FieldKey whitelist, conditional visibility, field-level validation: all component-agnostic.
- GDS error rendering pipeline: `WorkflowProblem → TempData → ViewModel → FieldErrors dict → PrismFieldContext → GDS partial`.
- **Conclusion:** Validation and error rendering will continue to work correctly regardless of component structure.

**Persistence & Storage**
- Fields carry `fieldKey` (storage/retrieval key).
- Whether fields live in fieldset, summary-list, or accordion, persistence is keyed to `fieldKey`.
- No change to storage layer needed.

**GDS Rendering**
- Bound to field metadata (label, validation constraints) via `PrismFieldContext`.
- Component wrapper is transparent to GDS rendering.

### ⚠️ MEDIUM RISK (4 Narrow Dependencies, Replaceable)

1. **Nonce skip logic** (`PrismWorkflowPageController.cs:140`): Check-answers (read-only) skips nonce generation.
   - Replace with: explicit `terminal` flag or response state check.

2. **Response state mapping** (`BusinessAppWorkflowEngine.cs:596-601`): "confirmation" → "complete", "status-timeline" → "defer", default → "render".
   - Replace with: explicit `responseState` metadata on StepDefinition.

3. **Partial view selection** (`workflowPage.cshtml:38-47`): Maps stepType to `_WorkflowStep-{Type}.cshtml`.
   - Replace with: infer partial from components + responseState.

4. **Terminal state detection** (`BusinessAppWorkflowEngine.cs:166`): Prompt policy checks `stepType == "confirmation"`.
   - Replace with: explicit `terminal` flag.

### 🔴 NO HIGH-RISK ITEMS IDENTIFIED

## Common Field Properties (Non-Negotiable)

Every input-carrying component must expose (at FieldRenderPayload level):
- `fieldKey` — Persistence, validation, nonce generation
- `fieldType` — Validation rules, HTML rendering
- `label` — GDS display label
- `hint` — GDS hint text
- `required` — Validation gate
- `minLength`, `maxLength`, `pattern`, `min`, `max` — Validation constraints
- `conditionalOn`, `visibleWhen`, `conditionalFields` — Conditional logic

**Note:** These properties are already component-independent in the validation and rendering pipelines.

## Recommendation

**SAFE TO PROCEED** — Replace stepType with explicit `terminal` + `responseState` metadata. All architectural layers (validation, persistence, GDS rendering) are component-agnostic and will continue to work correctly.
