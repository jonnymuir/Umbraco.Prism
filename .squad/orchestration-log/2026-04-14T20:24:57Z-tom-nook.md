## Outcome Summary

**Overall Assessment:** The current architecture is a **good fit for Prism and Umbraco 17 provided the boundary stays explicit**.

### Decision: Route-Hijacked Pages as Canonical Pattern

Treat the current member dashboard, workflow page, and workflow hub architecture as the right shape for Prism:

1. **Umbraco owns content-driven routing and page composition**
2. **Prism owns tenant resolution, auth/session renewal, and server-side workflow safety checks**
3. **Business App owns workflow state, field semantics, and progression rules**
4. **Client-side code stays progressive-enhancement only**

### Why This Fit Works

- Route-hijacked `RenderController`s and authored document types are the right Umbraco 17 shape for dashboard/workflow journeys
- `WorkflowPageController` plus nonce/validator services keep Prism acting as a secure workflow shell, not a second workflow engine
- `BusinessAppWorkflowClient` cleanly keeps workflow state external — the right Prism posture for tenant-aware integrations

### Key Architectural Strengths

- Server components stay thin: `PrismWorkflowFormTagHelper`, `PrismFieldTagHelper`, and archetype partials render contracts from the Business App rather than inventing workflow rules locally
- Member access is protected by Umbraco member validation before Business App calls
- Workflow UI does not duplicate Business App logic

### Architectural Debt to Prioritise

1. **Reduce demo-only route coupling**
   - `TestSiteSeedContract`, seeded fallback URLs, and direct view-path workaround in `MemberDashboardController` should not be treated as canonical production guidance
   - Clean these up before using TestSite as a reference for other projects

2. **Avoid duplicating workflow truth in Prism UI layers**
   - No claim-based field prepopulation that bypasses Business App intent
   - Dashboard-specific assumptions should not create a second source of truth

3. **Replace repeated published-content tree scans**
   - If workflow hubs grow beyond demo scale, implement a clearer resolver/index instead of re-scanning the tree

### Coupling Risks

- TestSite pattern mixes demo stability concerns with canonical Umbraco patterns
- Content-tree coupling could grow if new dashboard surfaces are added without clear resolver boundaries
