# Service Request Hub and conditional fields

These are the two advanced service blueprint patterns most package consumers need after the basic happy path: resumable journeys and progressively-disclosed inputs.

## Service Request Hub

The service request hub is the package's answer to "where does the user go when this journey is not a single straight-through form?"

`ServiceRequestHubController` and `Views/serviceRequestHub.cshtml` currently:

- fetch all service requests for the authenticated member,
- split them into in-progress and completed lists,
- resolve the matching `touchpointPage` by `blueprintKey`,
- append `instanceId` so users continue the right instance.

### Instance policies and the hub

| Policy | User experience |
| --- | --- |
| `single` | The hub is optional but still useful for status and history |
| `multiple` | The hub becomes the main way to distinguish concurrent requests |
| `prompt` | The service blueprint page can show an instance picker before creating a new request |

Prompt-mode instance picking is currently rendered by `Views/Partials/_WorkflowHub-InstancePicker.cshtml`.

## Conditional fields

Prism supports two related but distinct conditional patterns.

### 1. Simple dependent visibility

Use `ConditionalOn` + `VisibleWhen` when one field should appear only when another field has a specific value.

The `community-enquiry` seed demonstrates this pattern:

```json
{
  "type": "text",
  "fieldKey": "enquiry-type-detail",
  "label": "Please specify your enquiry type",
  "conditionalOn": "enquiry-type",
  "visibleWhen": "Other"
}
```

This is ideal when the revealed child is still just a normal field.

### 2. Option-specific child component trees

Use `ConditionalChildren` on radios or checkbox lists when selecting an option should reveal a nested group of components.

Fluent builder example:

```csharp
.Radios("contact-method", "How should we contact you?", new[] { "email", "phone", "other" },
    conditional: c => c.When("other", o => o
        .TextInput("contact-other", "Tell us how", required: true)))
```

This is the more expressive pattern because the revealed content can be more than one field.

## Validation behaviour for hidden fields

The validator deliberately skips hidden conditional fields. That means:

- authors can safely mark a conditional child required,
- the field only becomes required when it is actually visible,
- stale hidden values are not treated as an active submission requirement.

## Summary lists, waiting states, and task lists

These patterns commonly appear alongside hub-friendly service blueprints.

### Summary list

- authored with `SummaryListComponent`
- usually produces `check-answers`
- can emit `change:{stateKey}` actions via `ChangeStateKey`

### Waiting state

- authored with `WaitingComponent`
- produces `ResponseState = defer`
- carries `PollAfterMs`, `ExpectedWaitSeconds`, `AllowDefer`, and optional `DeferMessage`
- works best when the hub gives the user a clear place to resume later

### Task list

- authored with `TaskListComponent`
- produces the `task-list` shell
- can be explicit or auto-generated by the engine depending on your use case

## Practical authoring advice

- Prefer `ConditionalOn` / `VisibleWhen` for one-field reveals.
- Prefer `ConditionalChildren` when the reveal is a mini sub-form.
- Add a service request hub whenever users may pause, wait, or run more than one instance.
- Pair waiting states with a hub or prompt policy so the journey still feels navigable.
